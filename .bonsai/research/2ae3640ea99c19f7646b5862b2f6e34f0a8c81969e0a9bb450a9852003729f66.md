## Summary

Cannot upload files to the Dynamic WebDAV directory: `webdav put` always fails with 403 · Issue #719 · SalesforceCommerceCloud/b2c-developer-tooling

## Compressed

Follow-up to [#657] (implemented in [#706]).

**Describe the bug**

Uploading a file into the Dynamic WebDAV directory does not work. `b2c webdav put --root=dynamic` always fails with `403 Forbidden`, even when the destination directory already exists and is readable with `b2c webdav ls`.

The first request the command sends is an `MKCOL` against `Sites/Dynamic` — the WebDAV root itself, not the destination path.

This is not a credentials or permissions problem.

This makes the CLI unusable for the main use case [#657] was filed for: uploading velocity templates and other site-scoped mock data to `Sites/Dynamic/<site-id>/`.

**Command and output**

First, confirm the destination directory exists and is readable:

$ b2c webdav ls -r dynamic "\[Site ID\]/aaa/bbb/ccc" INFO: Listing Dynamic/\[Site ID\]/aaa/bbb/ccc...

Then attempt the upload into that existing directory:

b2c webdav put ./sample.vm "\[Site ID\]/aaa/bbb/ccc/" --root=dynamic --debug

Debug output

```
[13:51:51.781] INFO: Uploading /path/to/sample.vm to Dynamic/[Site ID]/aaa/bbb/ccc/sample.vm...
[13:51:51.783] DEBUG: [WebDAV REQ] MKCOL https://<instance>.my.commercecloud.salesforce.com/on/demandware.servlet/webdav/Sites/Dynamic
    command: "webdav:put"
    method: "MKCOL"
    url: "https://<instance>.my.commercecloud.salesforce.com/on/demandware.servlet/webdav/Sites/Dynamic"
[13:51:51.993] DEBUG: [WebDAV RESP] MKCOL https://<instance>.my.commercecloud.salesforce.com/on/demandware.servlet/webdav/Sites/Dynamic 403 209ms
    command: "webdav:put"
    method: "MKCOL"
    url: "https://<instance>.my.commercecloud.salesforce.com/on/demandware.servlet/webdav/Sites/Dynamic"
    status: 403
[13:51:53.259] ERROR: MKCOL failed: 403 Forbidden
    command: "webdav:put"
 ›   Error: MKCOL failed: 403 Forbidden
```

Note the URL on the failing request: it is neither the file nor its parent directory, but the root.

**Environment**

*   b2c-cli version: `@salesforce/b2c-cli/2.2.1 darwin-arm64 node-v22.22.0`
*   Node.js version: `v22.22.0`
*   OS: macOS 26.6.2 (arm64)
*   Target instance: ODS
*   Auth: OAuth client-credentials (also reproduced with `--auth-methods basic`)

**Additional context**

Every `REMOTE` path form produces the identical single request and failure:

| REMOTE argument / flags | Result |
| --- | --- |
| [Site ID]/aaa/bbb/ccc/ (trailing slash, "keeps filename" form) | MKCOL /Sites/Dynamic → 403 |
| [Site ID]/aaa/bbb/ccc/sample.vm (explicit filename) | MKCOL /Sites/Dynamic → 403 |
| /[Site ID]/aaa/bbb/ccc/sample.vm (leading slash) | MKCOL /Sites/Dynamic → 403 |
| --auth-methods basic instead of OAuth | MKCOL /Sites/Dynamic → 403 |

Read vs. write behaviour with the same credentials:

| Request | Target URL | Result |
| --- | --- | --- |
| ls (no path) | /Sites/Dynamic | 403 |
| ls [Site ID]/aaa | /Sites/Dynamic/[Site ID]/aaa | 200 |
| get [Site ID]/aaa/bbb/ccc/test.txt | /Sites/Dynamic/[Site ID]/aaa/bbb/ccc/test.txt | 200 |
| put (first request) | /Sites/Dynamic | 403 |

Two things appear to combine to cause this.

**1\. `ensureParentDirectories` includes the root segment.** In `commands/webdav/put.js`, the path it walks is the full path _including_ the root name (`Dynamic/[Site ID]/aaa/...`), so the first iteration targets `Dynamic`:

async ensureParentDirectories(fullPath) {
    const parts \= fullPath.split('/').filter(Boolean);
    parts.pop();
    let currentPath \= '';
    for (const part of parts) {
        currentPath \= currentPath ? \`${currentPath}/${part}\` : part;
        await this.instance.webdav.mkcol(currentPath);
    }
}

```
parts = [Dynamic, [Site ID], aaa, bbb, ccc]
iteration 1: currentPath = "Dynamic"              → mkcol → 403 → throws
iteration 2: currentPath = "Dynamic/[Site ID]"  → never reached
```

`commands/webdav/mkdir.js` has the same loop.

**2\. `mkcol` treats only 405 as "already exists".** In `@salesforce/b2c-tooling-sdk`, `clients/webdav.js`:

async mkcol(path) {
    const response \= await this.request(path, { method: 'MKCOL' });
    // 201 = created, 405 = already exists (acceptable)
    if (!response.ok && response.status !== 405) {
        throw new HTTPError(\`MKCOL failed: ...\`, response, 'MKCOL');
    }
}

On IMPEX, `MKCOL /Sites/Impex` returns 405 and the loop passes through harmlessly.

**Expected behaviour**

`put` should upload into an existing Dynamic directory, and should not send any request to the WebDAV root, which always exists and can never be created.

**Suggested fix**

Skip the root segment in `ensureParentDirectories` — the WebDAV root is guaranteed to exist for every `--root` value, so `MKCOL` on it is never useful. For `dynamic` specifically, the `<site-id>` segment is also system-managed and cannot be created, so it is a reasonable candidate to skip as well.

Separately, treating only 405 as "already exists" in `mkcol` is fragile. Either probe with `PROPFIND` before `MKCOL`, or do not auto-create parents at all and let `put` fail with the documented behaviour.

Thanks!

Reacted by Charles Lavery

SFCC rejects that path, so the command aborts before ever reaching the directory you asked for. `b2c webdav mkdir` fails identically, so the workaround the docs suggest ("Parent directories must exist — use `webdav mkdir` to create them") does not help either.

This is not a credentials or permissions problem. I uploaded the same file to the same directory through the **Business Manager WebDAV UI in a browser** and it succeeded, so the WebDAV access key is valid and the account does have write permission on `Sites/Dynamic/[Site ID]/`. `ls` and `get` through the CLI also work fine with the same credentials for any path under the site ID — only the root itself rejects requests.
