## [9\.] [Using Service Bindings with HTTP]

The use of any protocol with SVCB requires a protocol\-specific mapping specification.

To enable special handling for HTTP use cases, the HTTPS RR type is defined as a SVCB-compatible RR type, specific to the "https" and "http" schemes. Clients MUST NOT perform SVCB queries or accept SVCB responses for "https" or "http" schemes.[¶]

## Detailed

## [9\.](https://www.rfc-editor.org/info/rfc9460/#section-9) [Using Service Bindings with HTTP](https://www.rfc-editor.org/info/rfc9460/#name-using-service-bindings-with)

The use of any protocol with SVCB requires a protocol\-specific mapping specification. This section specifies the mapping for the "http" and "https" URI schemes \[[HTTP](https://www.rfc-editor.org/info/rfc9460/#RFC9110)\].[¶](https://www.rfc-editor.org/info/rfc9460/#section-9-1)

To enable special handling for HTTP use cases, the HTTPS RR type is defined as a SVCB-compatible RR type, specific to the "https" and "http" schemes. Clients MUST NOT perform SVCB queries or accept SVCB responses for "https" or "http" schemes.[¶](https://www.rfc-editor.org/info/rfc9460/#section-9-2)

The presentation format of the record is:[¶](https://www.rfc-editor.org/info/rfc9460/#section-9-3)

All the SvcParamKeys defined in [Section 7](https://www.rfc-editor.org/info/rfc9460/#keys) are permitted for use in HTTPS RRs. The default set of ALPN IDs is the single value "http/1.1". The "automatically mandatory" keys ([Section 8](https://www.rfc-editor.org/info/rfc9460/#mandatory)) are "port" and "no\-default\-alpn". (As described in [Section 8](https://www.rfc-editor.org/info/rfc9460/#mandatory), clients must either implement these keys or ignore any RR in which they appear.) Clients that restrict the destination port in "https" URIs (e.g., using the "bad ports" list from \[[FETCH](https://www.rfc-editor.org/info/rfc9460/#FETCH)\]) SHOULD apply the same restriction to the "port" SvcParam.[¶](https://www.rfc-editor.org/info/rfc9460/#section-9-5)

The presence of an HTTPS RR for an origin also indicates that clients should connect securely and use the "https" scheme, as discussed in [Section 9.5](https://www.rfc-editor.org/info/rfc9460/#hsts). This allows HTTPS RRs to apply to pre-existing "http" scheme URLs, while ensuring that the client uses a secure and authenticated connection.[¶](https://www.rfc-editor.org/info/rfc9460/#section-9-6)

The HTTPS RR parallels the concepts introduced in "HTTP Alternative Services" \[[AltSvc](https://www.rfc-editor.org/info/rfc9460/#RFC7838)\]. Clients and servers that implement HTTPS RRs are not required to implement Alt-Svc.[¶](https://www.rfc-editor.org/info/rfc9460/#section-9-7)
