# Managed Runtime Overview

[Managed Runtime] provides the infrastructure to deploy, host, and monitor your PWA Kit storefront.

:::important Managed Runtime only supports applications created from a PWA Kit template.

This guide covers the main parts of Managed Runtime and how to access it.

:::important Before you can use Managed Runtime and Runtime Admin, ask your B2C Commerce administrator to add one of these roles to your account in Account Manager: **Managed Runtime User** or **Managed Runtime Admin**. :::

## Environments

An **environment** is the term used to describe all of the cloud infrastructure and configuration values for a particular storefront hosted by Managed Runtime.

:::note In the [Managed Runtime API], environments are called “targets,” but both terms refer to the same thing. :::

Because environments run on highly efficient microservices that automatically scale up and down, you can create as many environments as you need at no additional cost.

### Production Environments

Environments marked as production are prioritized for monitoring by the Salesforce Support team and receive additional internal monitoring.

1. Use the Runtime Admin tool. Step-by-step instructions for creating an environment or editing an existing environment are found in the [Environments] section of the Administration guide.
2. Use the Managed Runtime API. The [projects_target_create] and [projects_target_partial_update] endpoints both feature the `is_production` parameter. To mark an environment as production with these endpoints, set `is_production` to `true`.

:::important By default, organizations have a production environment limit of 0. Before going live, contact Support to increase your production environment limit. :::

Starting September 29, 2026, an environment can be marked as production only if it's associated with a Staging or Production B2C Commerce instance.

Marking an environment as production doesn't affect access to Log Center logs and metrics. Log Center logs and metrics can be enabled for any environment associated with a B2C Commerce instance, regardless of the production flag.

## Bundles

The storefront code that runs on an environment is called a **bundle**. Use the developer tools included in PWA Kit to generate a bundle and push it to Managed Runtime.

:::note A bundle is a snapshot of your code at a specific point in time.

After pushing the bundle, you can use the Runtime Admin or Managed Runtime API to designate that bundle as “deployed.” Each project can have multiple bundles, but each environment can have only one bundle that's designated as deployed.

## Projects and Organizations

To help you manage multiple environments, each environment also belongs to a **project** and each project belongs to an **organization**. A Managed Runtime user can belong to multiple organizations to separate different work streams.

Each organization can have a maximum of 100 total environments.

Organizations and user organization membership is determined by settings in Account Manager. Members can only interact with the projects in Managed Runtime that they’ve been assigned a project role to.

:::important To assign a user the admin organization membership, contact Salesforce Support. :::

## Users, Abilities, and Roles

All users must be assigned the `Managed Runtime User` or `Managed Runtime Admin` via [Account Manager] for accessing Managed Runtime.

### Organization Roles and Permissions

Any user can have the following capabilities for a Managed Runtime organization:

- **Browse:** View all projects for an Organization.
- **Certificate:** View or manage TLS Certificates for an organization.

### Project Roles and Permissions

Any user can have the following capabilities for a Managed Runtime project:

- **Browse:** View the project in Runtime Admin.
- **Manage Redirects:** Manage redirects for the project. Please review the [Redirects documentation] to learn more.
- **Deploy:** Deploy new bundles or revert the deployment to an older bundle.
- **Manage Team:** View, add, invite, remove, and edit the roles of team members for the project.
- **Access Logs:** Tail logs across all environments.
- **View and Manage Environment Variables:** See and manage environment variables in each environment. See [Environment Variables].

Each user is assigned a project role that determines which abilities they have. (A user can only have *one* role.) Project roles can be assigned to any user within an organization.

The following table shows which abilities are associated with each project role:

| Project Role | Browse | Manage Redirects | Deploy | Manage Team | Access Logs | View and Manage Environment Variables |
| :----------- | :----- | :--------------- | :----- | :---------- | :---------- | :------------------------------------ |
| Admin        | Yes    | Yes              | Yes    | Yes         | Yes         | Yes                                   |
| Developer    | Yes    | Yes              | Yes    | No          | Yes         | Yes                                   |
| Marketer     | Yes    | Yes              | No     | No          | No          | No                                    |
| Viewer       | Yes    | No               | No     | No          | No          | No                                    |

## App Server

Within each Managed Runtime environment, the [React] app in the published bundle runs inside a [Node.js] environment.

Because PWA Kit’s rendering and routing system handles the differences between local development environments and Managed Runtime environments, your code runs in a predictable way when you deploy it.

Currently, the App Server supports Transport Layer Security (TLS) versions 1.2 and greater.

### Environment Variables

Code running on the App Server has access to the following environment variables:

- `DEPLOY_TARGET`: ID of the environment.
- `EXTERNAL_DOMAIN_NAME`: The domain name set on the environment.
- `MOBIFY_PROPERTY_ID`: ID of the project that the environment belongs to.

## Edge Services

Supporting the app server are several edge services, including:

- A web application firewall (WAF) to protect your environments from attackers
- A proxy server to speed up API requests
- A content delivery network (CDN) to cache requests and speed up page loading
- Edge functions that process requests and handle redirects

The proxy server and CDN are covered in detail in our guide to [Proxying Requests].

Managed Runtime’s edge services are strategically distributed throughout our public cloud infrastructure.

## Admin Tools

To manage the settings for your organizations, projects, environments, and bundles, we offer two different tools:

1. The [Managed Runtime Admin], a web-based UI.
2. The [Managed Runtime API], a REST API that offers the same functionality as the web-based tool and some additional capabilities.

Use the Runtime Admin tool for routine tasks, such as deploying a new code bundle to an environment.

The admin tools give you a self-serve way to configure many settings, including:

- Allowed IP addresses
- Allowed access control headers
- Currently deployed bundle
- Deployment region
- Proxies
- Redirects
- User permissions
- Production environment flag

Access to the admin tools is controlled with Account Manager roles and an API key.

Fun fact: Like your storefront, the Runtime Admin tool is a headless React app that is deployed to Managed Runtime.

## Constraints

While building your storefront, keep the following constraints of Managed Runtime environments in mind:

### Environments

- Environments only respond to requests whose HTTP `Host` header matches their External Hostname set in Runtime Admin.
- A hostname can be set as the External Hostname for only one environment at a time. Setting a hostname that's already in use by another environment fails.
- The path `/` only accepts HTTP GET requests.
- Request and response size can’t exceed 6 MB.
- The maximum size of the HTTP request line and headers is 10240 bytes. Requests exceeding this size return an [HTTP 413 Content Too Large].
  - Of the 10,240 bytes, 1,500 bytes are reserved for internal use, 1,800 bytes for authorization headers, and 1,000 bytes for Salesforce B2C Commerce API (SCAPI). 5,940 bytes are left for custom request headers, including cookies.
- Cookies, including the HTTP request `Cookie` and HTTP response `Set-Cookie` header aren't supported by default. They can be enabled by setting the `allow_cookies` attribute on an environment with the [projects_target_partial_update] endpoint. You can also enable cookies in the [Environment Settings] in [Runtime Admin]. Cookies are supported in PWA Kit version 3.1.0 or greater. See [Personalize with Cookies].
- Requests with headers that start with `_` are not supported. These requests will be dropped.
- HTTP requests originating from Managed Runtime environments don't use fixed IP addresses. To allow list requests from the App Server use the [AWS IP Range] for `EC2`. To allow list requests from Proxies, use `CLOUDFRONT_ORIGIN_FACING`.
- The path prefix `/mobify` is reserved for managed endpoints. These endpoints include:
  - `/mobify/ping`: Returns an HTTP 200 response code when the environment is operating correctly.
  - `/mobify/redirect/$path`: Returns a similar response as [projects_target_redirect_retrieve].
  - `/mobify/proxy/$name`: Returns a response from a [proxy].
- You can bypass the CDN cache using the HTTP request header: `x-mobify-cachebreaker: 1`
- Environment IP Allowlists support up to 250 IP addresses. This limit can't be raised.
- Environment access control headers support up to 2 headers, or up to 4 for Storefront Next environments. Each header:
  - Can contain up to 128 characters.
  - Can be a combination of alphanumeric characters and - and \_ characters
  - See [Access Control Headers].

### Rendering

- The execution time for App Server requests is limited to 20 seconds for production environments and 16 seconds for non-production environments. After this time, an HTTP 502 is returned.
- Unhandled promise rejections break app rendering.

### Deployments

- The maximum size for bundles is 400 MB and the maximum size of all `ssr_only` and `ssr_shared` files within the bundle is 249 MB.
- Static assets that can be uploaded and served are limited to the following content types: `application/javascript`, `application/json`, `image/png` ,`image/gif`, `image/jpeg`, `image/svg+xml`, `image/webp`, `text/css`, `text/plain` and fonts (`ttf`, `woff`, `woff2`, `otf`, etc). All other content types need to be served by an external system.

### Proxies

Managed Runtime Proxies have different [constraints].

## Environments

An **environment** is the term used to describe all of the cloud infrastructure and configuration values for a particular storefront hosted by Managed Runtime. Environments are used to separate your production storefront from other storefronts that are deployed for other purposes, such as development or testing.

:::note
In the [Managed Runtime API](https://developer.salesforce.com/docs/commerce/pwa-kit-managed-runtime/references/mrt-admin?meta=Summary), environments are called “targets,” but both terms refer to the same thing.
:::

Because environments run on highly efficient microservices that automatically scale up and down, you can create as many environments as you need at no additional cost. For example, you could create a short-lived environment dedicated to a single agile development sprint or for a single user story within that sprint. When you no longer need an environment, we encourage you to delete them.

### Production Environments

Environments marked as production are prioritized for monitoring by the Salesforce Support team and receive additional internal monitoring. Non-production environments have lower capacity limits, reflecting their use for development and testing traffic rather than live storefront traffic. To mark an environment as a production, you have two choices:

1. Use the Runtime Admin tool. Step-by-step instructions for creating an environment or editing an existing environment are found in the [Environments](https://developer.salesforce.com/docs/commerce/pwa-kit-managed-runtime/guide/managed-runtime-administration.md#environments) section of the Administration guide.
2. Use the Managed Runtime API. The [projects_target_create](https://developer.salesforce.com/docs/commerce/pwa-kit-managed-runtime/references/mrt-admin?meta=projects_target_create) and [projects_target_partial_update](https://developer.salesforce.com/docs/commerce/pwa-kit-managed-runtime/references/mrt-admin?meta=projects_target_partial_update) endpoints both feature the `is_production` parameter. To mark an environment as production with these endpoints, set `is_production` to `true`.

:::important
By default, organizations have a production environment limit of 0. Before going live, contact Support to increase your production environment limit.
:::

Starting September 29, 2026, an environment can be marked as production only if it's associated with a Staging or Production B2C Commerce instance. Associate your production environments with a Staging or Production instance now to avoid disruption. See [Edit Environment Settings](/docs/commerce/b2c-commerce/guide/managed-runtime-administration.md#edit-environment-settings).

Marking an environment as production doesn't affect access to Log Center logs and metrics. Log Center logs and metrics can be enabled for any environment associated with a B2C Commerce instance, regardless of the production flag. See [Debug Using Log Center](/docs/commerce/b2c-commerce/guide/debugging.md#debug-using-log-center).

## Bundles

The storefront code that runs on an environment is called a **bundle**. Use the developer tools included in PWA Kit to generate a bundle and push it to Managed Runtime.

:::note
A bundle is a snapshot of your code at a specific point in time. It’s *immutable*: After a bundle has been created, it can’t be changed. Having this complete and accurate history of bundles makes troubleshooting deployments easier.
:::

After pushing the bundle, you can use the Runtime Admin or Managed Runtime API to designate that bundle as “deployed.” Each project can have multiple bundles, but each environment can have only one bundle that's designated as deployed. You can change which bundle is designated as deployed at any time. For more information, see [Push and Deploy Bundles](/docs/commerce/b2c-commerce/guide/pushing-and-deploying-bundles.md).

A Managed Runtime user can belong to multiple organizations to separate different work streams.

## App Server

Within each Managed Runtime environment, the [React](https://reactjs.org/) app in the published bundle runs inside a [Node.js](https://nodejs.org/) environment. To respond to page requests and render the results, we use the [Express](https://expressjs.com/) web framework with the help of PWA Kit’s [rendering](/docs/commerce/b2c-commerce/guide/rendering.md) and [routing](/docs/commerce/b2c-commerce/guide/routing.md) systems. We call this combination of React, Node, and Express the **App Server**. (Although, technically speaking, the App Server runs on “serverless” technology.) The App Server is optimized to run on cloud infrastructure that offers low computing costs, high availability, fast rendering, and massive scaling capacity.

Because PWA Kit’s rendering and routing system handles the differences between local development environments and Managed Runtime environments, your code runs in a predictable way when you deploy it. This predictability unlocks your development team’s productivity by encouraging them to deploy bundles more frequently.

Currently, the App Server supports Transport Layer Security (TLS) versions 1.2 and greater.

### Environment Variables

Code running on the App Server has access to the following environment variables:

- `DEPLOY_TARGET`: ID of the environment.
- `EXTERNAL_DOMAIN_NAME`: The domain name set on the environment.
- `MOBIFY_PROPERTY_ID`: ID of the project that the environment belongs to.

## Edge Services

Supporting the app server are several edge services, including:

- A web application firewall (WAF) to protect your environments from attackers
- A proxy server to speed up API requests
- A content delivery network (CDN) to cache requests and speed up page loading
- Edge functions that process requests and handle redirects

The proxy server and CDN are covered in detail in our guide to [Proxying Requests](/docs/commerce/b2c-commerce/guide/proxying-requests.md). The edge function called the request processor is covered in our guide to [Maximizing Your Cache Hit Ratio](/docs/commerce/b2c-commerce/guide/maximizing-your-cache-hit-ratio.md).

Managed Runtime’s edge services are strategically distributed throughout our public cloud infrastructure. Each service is located as close to the user as possible for faster performance.

## Admin Tools

To manage the settings for your organizations, projects, environments, and bundles, we offer two different tools:

1. The [Managed Runtime Admin](https://runtime.commercecloud.com/), a web-based UI.
2. The [Managed Runtime API](https://developer.salesforce.com/docs/commerce/pwa-kit-managed-runtime/references?meta=managed-runtime-api\:Summary), a REST API that offers the same functionality as the web-based tool and some additional capabilities.

Use the Runtime Admin tool for routine tasks, such as deploying a new code bundle to an environment. Use the API whenever you need programmatic control, such as automatically creating an environment as part of a continuous integration script.

The admin tools give you a self-serve way to configure many settings, including:

- Allowed IP addresses
- Allowed access control headers
- Currently deployed bundle

- Redirects

Access to the admin tools is controlled with Account Manager roles and an API key. For continuous integration (CI) and continuous delivery (CD) processes, dedicated bot users with their own API keys are typically provisioned by your organization.

Fun fact: Like your storefront, the Runtime Admin tool is a headless React app that is deployed to Managed Runtime.
