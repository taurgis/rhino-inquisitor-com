## Summary

2\. The SVCB Record Type > 2.4. Interpretation

## Compressed

### [2.4.] [Interpretation]

#### [2.4.1.] [SvcPriority]

When SvcPriority is 0, the SVCB record is in AliasMode ([Section 2.4.2]).

Within a SVCB RRset, all RRs SHOULD have the same mode.

RRsets are explicitly unordered collections, so the SvcPriority field is used to impose an ordering on SVCB RRs.

When receiving an RRset containing multiple SVCB records with the same SvcPriority value, clients SHOULD apply a random shuffle within a priority level to the records before using them, to ensure uniform load balancing.[¶]

#### [2.4.2.] [AliasMode]

In AliasMode, the SVCB record aliases a service to a TargetName.

The primary purpose of AliasMode is to allow aliasing at the zone apex, where CNAME is not allowed (see, for example, \[[RFC1912]\], [Section 2.4]). (See [Section 6] for aliasing of SVCB-compatible RR types.) Unlike CNAME, AliasMode records do not affect the resolution of other RR types and apply only to a specific service, not an entire domain name.[¶]

The AliasMode TargetName SHOULD NOT be equal to the owner name, as this would result in a loop. Zone-file parsers MAY emit a warning if an AliasMode record has SvcParams.

For example, the operator of "foo://example.com:8080" could point requests to a service operating at "foosvc.example.net" by publishing:[¶]

Using AliasMode maintains a separation of concerns: the owner of "foosvc.example.net" can add or remove ServiceMode SVCB records without requiring a corresponding change to "example.com".

AliasMode is especially useful for SVCB-compatible RR types that do not require an underscore prefix, such as the HTTPS RR type.

Note that the SVCB record's owner name MAY be the canonical name of a CNAME record, and the TargetName MAY be the owner of a CNAME record.

To avoid unbounded alias chains, clients and recursive resolvers MUST impose a limit on the total number of SVCB aliases they will follow for each resolution request. This limit MUST NOT be zero, i.e., implementations MUST be able to follow at least one AliasMode record.

Zones that require following multiple AliasMode records could encounter compatibility and performance issues.[¶]

As legacy clients will not know to use this record, service operators will likely need to retain fallback AAAA and A records alongside this SVCB record, although in a common case the target of the SVCB record might offer better performance, and therefore would be preferable for clients implementing this specification to use.[¶]

AliasMode records only apply to queries for the specific RR type. For example, a SVCB record cannot alias to an HTTPS record or vice versa.[¶]

#### [2.4.3.] [ServiceMode]

In ServiceMode, the TargetName and SvcParams within each RR associate an alternative endpoint for the service with its connection parameters.[¶]

Each protocol scheme that uses SVCB MUST define a protocol mapping that explains how SvcParams are applied for connections of that scheme. Unless specified otherwise by the protocol mapping, clients MUST ignore any SvcParam that they do not recognize.[¶]

Some SvcParams impose requirements on other SvcParams in the RR.

## Detailed

### [2.4.](https://www.rfc-editor.org/info/rfc9460/#section-2.4) [Interpretation](https://www.rfc-editor.org/info/rfc9460/#name-interpretation)

#### [2.4.1.](https://www.rfc-editor.org/info/rfc9460/#section-2.4.1) [SvcPriority](https://www.rfc-editor.org/info/rfc9460/#name-svcpriority)

When SvcPriority is 0, the SVCB record is in AliasMode ([Section 2.4.2](https://www.rfc-editor.org/info/rfc9460/#alias-mode)). Otherwise, it is in ServiceMode ([Section 2.4.3](https://www.rfc-editor.org/info/rfc9460/#service-mode)).[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.1-1)

Within a SVCB RRset, all RRs SHOULD have the same mode. If an RRset contains a record in AliasMode, the recipient MUST ignore any ServiceMode records in the set.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.1-2)

RRsets are explicitly unordered collections, so the SvcPriority field is used to impose an ordering on SVCB RRs. A smaller SvcPriority indicates that the domain owner recommends the use of this record over ServiceMode RRs with a larger SvcPriority value.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.1-3)

When receiving an RRset containing multiple SVCB records with the same SvcPriority value, clients SHOULD apply a random shuffle within a priority level to the records before using them, to ensure uniform load balancing.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.1-4)

#### [2.4.2.](https://www.rfc-editor.org/info/rfc9460/#section-2.4.2) [AliasMode](https://www.rfc-editor.org/info/rfc9460/#name-aliasmode)

In AliasMode, the SVCB record aliases a service to a TargetName. SVCB RRsets SHOULD only have a single RR in AliasMode. If multiple AliasMode RRs are present, clients or recursive resolvers SHOULD pick one at random.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.2-1)

The primary purpose of AliasMode is to allow aliasing at the zone apex, where CNAME is not allowed (see, for example, \[[RFC1912](https://www.rfc-editor.org/info/rfc9460/#RFC1912)\], [Section 2.4](https://rfc-editor.org/rfc/rfc1912#section-2.4)). In AliasMode, the TargetName will be the name of a domain that resolves to SVCB, AAAA, and/or A records. (See [Section 6](https://www.rfc-editor.org/info/rfc9460/#svcb-compatible) for aliasing of SVCB-compatible RR types.) Unlike CNAME, AliasMode records do not affect the resolution of other RR types and apply only to a specific service, not an entire domain name.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.2-2)

The AliasMode TargetName SHOULD NOT be equal to the owner name, as this would result in a loop. In AliasMode, recipients MUST ignore any SvcParams that are present. Zone-file parsers MAY emit a warning if an AliasMode record has SvcParams. The use of SvcParams in AliasMode records is currently not defined, but a future specification could extend AliasMode records to include SvcParams.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.2-3)

For example, the operator of "foo://example.com:8080" could point requests to a service operating at "foosvc.example.net" by publishing:[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.2-4)

Using AliasMode maintains a separation of concerns: the owner of "foosvc.example.net" can add or remove ServiceMode SVCB records without requiring a corresponding change to "example.com". Note that if "foosvc.example.net" promises to always publish a SVCB record, this AliasMode record can be replaced by a CNAME at the same owner name.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.2-6)

AliasMode is especially useful for SVCB-compatible RR types that do not require an underscore prefix, such as the HTTPS RR type. For example, the operator of "https://example.com" could point requests to a server at "svc.example.net" by publishing this record at the zone apex:[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.2-7)

Note that the SVCB record's owner name MAY be the canonical name of a CNAME record, and the TargetName MAY be the owner of a CNAME record. Clients and recursive resolvers MUST follow CNAMEs as normal.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.2-9)

To avoid unbounded alias chains, clients and recursive resolvers MUST impose a limit on the total number of SVCB aliases they will follow for each resolution request. This limit MUST NOT be zero, i.e., implementations MUST be able to follow at least one AliasMode record. The exact value of this limit is left to implementations.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.2-10)

Zones that require following multiple AliasMode records could encounter compatibility and performance issues.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.2-11)

As legacy clients will not know to use this record, service operators will likely need to retain fallback AAAA and A records alongside this SVCB record, although in a common case the target of the SVCB record might offer better performance, and therefore would be preferable for clients implementing this specification to use.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.2-12)

AliasMode records only apply to queries for the specific RR type. For example, a SVCB record cannot alias to an HTTPS record or vice versa.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.2-13)

#### [2.4.3.](https://www.rfc-editor.org/info/rfc9460/#section-2.4.3) [ServiceMode](https://www.rfc-editor.org/info/rfc9460/#name-servicemode)

In ServiceMode, the TargetName and SvcParams within each RR associate an alternative endpoint for the service with its connection parameters.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.3-1)

Each protocol scheme that uses SVCB MUST define a protocol mapping that explains how SvcParams are applied for connections of that scheme. Unless specified otherwise by the protocol mapping, clients MUST ignore any SvcParam that they do not recognize.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.3-2)

Some SvcParams impose requirements on other SvcParams in the RR. A ServiceMode RR is called "self\-consistent" if its SvcParams all comply with each other's requirements. Clients MUST reject any RR whose recognized SvcParams are not self-consistent and MAY reject the entire RRset. To help zone operators avoid this condition, zone-file implementations SHOULD enforce self\-consistency as well.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.4.3-3)
