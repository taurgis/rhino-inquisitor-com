## Summary

9\. Using Service Bindings with HTTP > 9.2. Comparison with Alt-Svc

## Compressed

### [9.2.] [Comparison with Alt-Svc]

Publishing a ServiceMode HTTPS RR in DNS is intended to be similar to transmitting an Alt-Svc field value over HTTP, and receiving an HTTPS RR is intended to be similar to receiving that field value over HTTP.

#### [9.2.1.] [ALPN Usage]

Unlike Alt-Svc field values, HTTPS RRs can contain multiple ALPN IDs.

#### [9.2.2.] [Untrusted Channels]

HTTPS records do not require or provide any assurance of authenticity. (DNSSEC signing and verification, which would provide such assurance, are OPTIONAL.) The DNS resolution process is modeled as an untrusted channel that might be controlled by an attacker, so Alt-Svc parameters that cannot be safely received in this model MUST NOT have a corresponding defined SvcParamKey. For example, there is no SvcParamKey corresponding to the Alt-Svc "persist" parameter, because this parameter is not safe to accept over an untrusted channel.[¶]

#### [9.2.3.] [Cache Lifetime]

There is no SvcParamKey corresponding to the Alt-Svc "ma" (max age) parameter. Instead, server operators encode the expiration time in the DNS TTL.[¶]

The appropriate TTL value might be different from the "ma" value used for Alt-Svc, depending on the desired efficiency and agility. Some DNS caches incorrectly extend the lifetime of DNS records beyond the stated TTL, so server operators cannot rely on HTTPS RRs expiring on time.

#### [9.2.4.] [Granularity]

Sending Alt-Svc over HTTP allows the server to tailor the Alt-Svc field value specifically to the client. Therefore, HTTPS RRs are not suitable for uses that require single-client granularity.[¶]

## Detailed

### [9.2.](https://www.rfc-editor.org/info/rfc9460/#section-9.2) [Comparison with Alt-Svc](https://www.rfc-editor.org/info/rfc9460/#name-comparison-with-alt-svc)

Publishing a ServiceMode HTTPS RR in DNS is intended to be similar to transmitting an Alt-Svc field value over HTTP, and receiving an HTTPS RR is intended to be similar to receiving that field value over HTTP. However, there are some differences in the intended client and server behavior.[¶](https://www.rfc-editor.org/info/rfc9460/#section-9.2-1)

#### [9.2.1.](https://www.rfc-editor.org/info/rfc9460/#section-9.2.1) [ALPN Usage](https://www.rfc-editor.org/info/rfc9460/#name-alpn-usage)

Unlike Alt-Svc field values, HTTPS RRs can contain multiple ALPN IDs. The meaning and use of these IDs are discussed in [Section 7.1.2](https://www.rfc-editor.org/info/rfc9460/#use).[¶](https://www.rfc-editor.org/info/rfc9460/#section-9.2.1-1)

#### [9.2.2.](https://www.rfc-editor.org/info/rfc9460/#section-9.2.2) [Untrusted Channels](https://www.rfc-editor.org/info/rfc9460/#name-untrusted-channels)

HTTPS records do not require or provide any assurance of authenticity. (DNSSEC signing and verification, which would provide such assurance, are OPTIONAL.) The DNS resolution process is modeled as an untrusted channel that might be controlled by an attacker, so Alt-Svc parameters that cannot be safely received in this model MUST NOT have a corresponding defined SvcParamKey. For example, there is no SvcParamKey corresponding to the Alt-Svc "persist" parameter, because this parameter is not safe to accept over an untrusted channel.[¶](https://www.rfc-editor.org/info/rfc9460/#section-9.2.2-1)

#### [9.2.3.](https://www.rfc-editor.org/info/rfc9460/#section-9.2.3) [Cache Lifetime](https://www.rfc-editor.org/info/rfc9460/#name-cache-lifetime)

There is no SvcParamKey corresponding to the Alt-Svc "ma" (max age) parameter. Instead, server operators encode the expiration time in the DNS TTL.[¶](https://www.rfc-editor.org/info/rfc9460/#section-9.2.3-1)

The appropriate TTL value might be different from the "ma" value used for Alt-Svc, depending on the desired efficiency and agility. Some DNS caches incorrectly extend the lifetime of DNS records beyond the stated TTL, so server operators cannot rely on HTTPS RRs expiring on time. Shortening the TTL to compensate for incorrect caching is NOT RECOMMENDED, as this practice impairs the performance of correctly functioning caches and does not guarantee faster expiration from incorrect caches. Instead, server operators SHOULD maintain compatibility with expired records until they observe that nearly all connections have migrated to the new configuration.[¶](https://www.rfc-editor.org/info/rfc9460/#section-9.2.3-2)

#### [9.2.4.](https://www.rfc-editor.org/info/rfc9460/#section-9.2.4) [Granularity](https://www.rfc-editor.org/info/rfc9460/#name-granularity)

Sending Alt-Svc over HTTP allows the server to tailor the Alt-Svc field value specifically to the client. When using an HTTPS RR, groups of clients will necessarily receive the same SvcParams. Therefore, HTTPS RRs are not suitable for uses that require single-client granularity.[¶](https://www.rfc-editor.org/info/rfc9460/#section-9.2.4-1)
