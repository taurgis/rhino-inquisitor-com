2\. The SVCB Record Type > 2.3. SVCB Query Names

## Compressed

### [2.3.] [SVCB Query Names]

When querying the SVCB RR, a service is translated into a QNAME by prepending the service name with a label indicating the scheme, prefixed with an underscore, resulting in a domain name like "\_examplescheme.api.example.com.". This follows the Attrleaf naming pattern \[[Attrleaf]\], so the scheme MUST be registered appropriately with IANA (see [Section 11]).[¶]

Protocol mapping documents MAY specify additional underscore\-prefixed labels to be prepended.

See [Section 9.1] for information regarding HTTPS RR behavior.[¶]

When a prior CNAME or SVCB record has aliased to a SVCB record, each RR SHALL be returned under its own owner name, as in ordinary CNAME processing (\[[RFC1034]\], [Section 3.6.2]).

Note that none of these forms alter the origin or authority for validation purposes.

As an example, the owner of "example.com" could publish this record:[¶]

This record would indicate that "foo://api.example.com:8443" is aliased to "svc4.example.net".

This record would indicate that these services are served on port number 8004, which supports the protocol "bar" and its associated transport in addition to the default transport protocol for "foo://".[¶]

(Parentheses are used to ignore a line break in DNS zone-file presentation format, per [Section 5.1] of \[[RFC1035]\].)[¶]

## Detailed

### [2.3.](https://www.rfc-editor.org/info/rfc9460/#section-2.3) [SVCB Query Names](https://www.rfc-editor.org/info/rfc9460/#name-svcb-query-names)

When querying the SVCB RR, a service is translated into a QNAME by prepending the service name with a label indicating the scheme, prefixed with an underscore, resulting in a domain name like "\_examplescheme.api.example.com.". This follows the Attrleaf naming pattern \[[Attrleaf](https://www.rfc-editor.org/info/rfc9460/#RFC8552)\], so the scheme MUST be registered appropriately with IANA (see [Section 11](https://www.rfc-editor.org/info/rfc9460/#other-standards)).[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.3-1)

Protocol mapping documents MAY specify additional underscore\-prefixed labels to be prepended. For schemes that specify a port ([Section 3.2.3](https://rfc-editor.org/rfc/rfc3986#section-3.2.3) of \[[URI](https://www.rfc-editor.org/info/rfc9460/#RFC3986)\]), one reasonable possibility is to prepend the indicated port number if a non-default port number is specified. This document terms this behavior "Port Prefix Naming" and uses it in the examples throughout.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.3-2)

See [Section 9.1](https://www.rfc-editor.org/info/rfc9460/#httpsnames) for information regarding HTTPS RR behavior.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.3-3)

When a prior CNAME or SVCB record has aliased to a SVCB record, each RR SHALL be returned under its own owner name, as in ordinary CNAME processing (\[[RFC1034](https://www.rfc-editor.org/info/rfc9460/#RFC1034)\], [Section 3.6.2](https://rfc-editor.org/rfc/rfc1034#section-3.6.2)). For details, see the recommendations regarding aliases for clients ([Section 3](https://www.rfc-editor.org/info/rfc9460/#client-behavior)), servers ([Section 4](https://www.rfc-editor.org/info/rfc9460/#server-behavior)), and zones ([Section 10](https://www.rfc-editor.org/info/rfc9460/#zone-structures)).[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.3-4)

Note that none of these forms alter the origin or authority for validation purposes. For example, TLS clients MUST continue to validate TLS certificates for the original service name.[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.3-5)

As an example, the owner of "example.com" could publish this record:[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.3-6)

This record would indicate that "foo://api.example.com:8443" is aliased to "svc4.example.net". The owner of "example.net", in turn, could publish this record:[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.3-8)

This record would indicate that these services are served on port number 8004, which supports the protocol "bar" and its associated transport in addition to the default transport protocol for "foo://".[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.3-10)

(Parentheses are used to ignore a line break in DNS zone-file presentation format, per [Section 5.1](https://rfc-editor.org/rfc/rfc1035#section-5.1) of \[[RFC1035](https://www.rfc-editor.org/info/rfc9460/#RFC1035)\].)[¶](https://www.rfc-editor.org/info/rfc9460/#section-2.3-11)
