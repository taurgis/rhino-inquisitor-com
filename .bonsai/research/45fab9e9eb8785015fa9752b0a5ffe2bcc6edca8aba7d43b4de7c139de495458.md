## Compressed

### [5.5.] [Integration with Existing API Management Frameworks]

A Publisher may already utilise an API management framework to produce their API portfolio. These frameworks typically include the publication of API endpoint URIs, deprecation and redirection of legacy API versions, API usage policies and documentation, etc. The api-catalog well-known URI and API catalog document are intended to complement API management frameworks by facilitating the discovery of the framework's outputs -- API endpoints, usage policies, and documentation -- and are not intended to replace any existing API discovery mechanisms the framework has implemented.[¶]

Providers of such frameworks may include the production of an API catalog and the publication of the /.well\-known/api\-catalog URI as a final pre-release (or post-release) step in the release management workflow.

If the /.well\-known/api\-catalog URI has not been published previously, the framework provider should:[¶]

*   Collate and check the metadata for each API that will be included in the API catalog. This metadata is likely to already exist in the framework.[¶]
    
*   Determine which metadata to include in the API catalog following the requirements set out in [Section 4.1] and the considerations set out in [Section 5].[¶]
    
*   Map the chosen metadata to the format(s) described in [Section 4.2]. The structure suggested in [Appendix A.2] may be followed where only the hyperlinks to APIs are to be included in the API catalog. Where possible, the API catalog should include further metadata per the guidance in [Section 4.1]; in which case, the structure suggested in [Appendix A] can be utilised and adapted (ensuring compliance to \[[RFC9264]\]) to reflect the nature of the chosen metadata.[¶]
    
*   Publish the /.well\-known/api\-catalog URI following the guidance set out in [Section 2].[¶]
    

If the /.well\-known/api\-catalog URI has previously been published, the framework provider should:[¶]

*   Include a step in the release management lifecycle to refresh the API catalog following any changes in API hyperlinks or published metadata. This could include placing triggers on certain metadata fields, so that as they are updated in pre-production on the API framework, the updates are pushed to a pre-production copy of the API catalog to be pushed live when the release is published by the framework.[¶]

The following steps are recommended.[¶](https://www.rfc-editor.org/info/rfc9727/#section-5.5-2)

If the /.well\-known/api\-catalog URI has not been published previously, the framework provider should:[¶](https://www.rfc-editor.org/info/rfc9727/#section-5.5-3)

*   Collate and check the metadata for each API that will be included in the API catalog. This metadata is likely to already exist in the framework.[¶](https://www.rfc-editor.org/info/rfc9727/#section-5.5-4.1.1)
    
*   Determine which metadata to include in the API catalog following the requirements set out in [Section 4.1](https://www.rfc-editor.org/info/rfc9727/#api-catalog-contents) and the considerations set out in [Section 5](https://www.rfc-editor.org/info/rfc9727/#operations).[¶](https://www.rfc-editor.org/info/rfc9727/#section-5.5-4.2.1)
    
*   Map the chosen metadata to the format(s) described in [Section 4.2](https://www.rfc-editor.org/info/rfc9727/#api-catalog-formats). The structure suggested in [Appendix A.2](https://www.rfc-editor.org/info/rfc9727/#api-catalog-example-linkset-bookmarks) may be followed where only the hyperlinks to APIs are to be included in the API catalog. Where possible, the API catalog should include further metadata per the guidance in [Section 4.1](https://www.rfc-editor.org/info/rfc9727/#api-catalog-contents); in which case, the structure suggested in [Appendix A](https://www.rfc-editor.org/info/rfc9727/#api-catalog-example-linkset) can be utilised and adapted (ensuring compliance to \[[RFC9264](https://www.rfc-editor.org/info/rfc9727/#RFC9264)\]) to reflect the nature of the chosen metadata.[¶](https://www.rfc-editor.org/info/rfc9727/#section-5.5-4.3.1)
    
*   Publish the /.well\-known/api\-catalog URI following the guidance set out in [Section 2](https://www.rfc-editor.org/info/rfc9727/#usage).[¶](https://www.rfc-editor.org/info/rfc9727/#section-5.5-4.4.1)

*   Include a step in the release management lifecycle to refresh the API catalog following any changes in API hyperlinks or published metadata.
